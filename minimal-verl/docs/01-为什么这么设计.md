# 01. 为什么这么设计

> 解答 3 个关键问题：为什么选 TRL 而不是 verl、为什么选 Qwen2.5-0.5B、为什么用 FP32。
>
> 这些决策不只为本项目 —— 它们是 2026 年 macOS 端跑 Agentic RL 的"经验法则"。

---

## Q1: 为什么不直接用 verl？

**verl**（火山引擎的 RL 训练框架）依赖 vLLM/SGLang/FSDP **全部都是 NVIDIA CUDA-only**。在 macOS 上装 verl **几乎必然失败**（依赖装不上、CUDA kernels 没法编译）。

**TRL 的 GRPOTrainer**：
- 纯 PyTorch 实现，**全平台支持**（macOS/Linux/Windows）
- API 跟 verl 几乎一致（`GRPOTrainer` 类、`reward_funcs` 参数、组内 advantage 算法）
- **HuggingFace 官方维护**，bug 修复快、文档全

**血缘关系**：
```
verl 的 GRPO  ←─借鉴──  TRL 的 GRPOTrainer
                       ↑
                       我们用这个
```

学会 TRL 后迁 verl 容易（只改入口）。**这是工程上最稳的选择**。

## Q2: 为什么选 Qwen2.5-0.5B？

| 备选 | 优点 | 缺点 | 不选 |
|---|---|---|---|
| **Qwen2.5-0.5B** ✅ | 中文能力强、0.5B 最小可训、HF 下载快 | 比大模型弱 | — |
| Qwen2.5-1.5B | 更强 | 1.5B + 训练激活，24GB 内存紧张 | ❌ |
| SmolLM2-135M | 极小 | 中文能力差 | ❌ |
| TinyLlama-1.1B | 小 | **英文模型**，中文任务不行 | ❌ |

**内存估算（FP32）**：
```
模型权重:    ~1GB
训练激活:    ~2GB
mmap 等:     ~2GB
系统占用:    ~8GB
────────────────
总计:        < 16GB    ←  24GB 内存内安全
```

## Q3: 为什么用 FP32 不用 FP16/BF16？

**Apple Silicon (MPS) 的精度支持矩阵**：
- ✅ **FP32** —— 稳定
- ⚠️ **FP16** —— 部分算子有 bug，grad scaling 易出问题
- ⚠️ **BF16** —— 范围比 FP16 大但 MPS 训练时**有 loss spike 报告**

**0.5B 模型 + 24GB 内存 = FP32 完全不紧张**，没必要冒精度风险。**这是 MPS 上的"安全默认值"**。

如果将来换 7B+ 模型，FP32 会 OOM，那时再考虑：
- 先试 `bf16=True`（MPS 1.13+ 有改进）
- 不行就上 `accelerate` + `cpu_offload`

## Q4: 为什么用 ChatML messages 格式不用 Alpaca？

| 格式 | 优点 | 缺点 |
|---|---|---|
| **ChatML messages** ✅ | Qwen 原生训练格式；trl/llama-factory/ms-swift 都支持；GRPO 直接吃 messages 列表 | — |
| Alpaca `{instruction, input, output}` | 简单 | SFT 时要手拼 chat template；GRPO 多写拼接代码 |

**SFT/GRPO 都能直接吃 messages 列表** = 零代码转换。**选最省事的**。

---

## Q5: 为什么 8 条训练数据够 SFT 不够 GRPO？

**SFT** 是"有监督学习"——给定 (input, target)，算交叉熵 loss。**8 条数据训 3 epoch = 24 步**，每步都算 loss，模型有充分信号。

**GRPO** 是"组内相对比较"——**只有 4 个 completion 里有"对的"和"错的"才有训练信号**（advantage=0 不能更新模型）。
- 如果 4 个全对（reward=1, 1, 1, 1）→ 没法学
- 如果 4 个全错（reward=0, 0, 0, 0）→ 也没法学
- **只有 1 对 3 错**（reward=1, 0, 0, 0）→ advantage 才有意义

**SFT 后模型过拟合到训练集**（token acc 97.7%）→ 4 次采样经常全对（奖励 = 1.0 全 1.0）→ 训练信号消失。

**这正是工业界 RL 必须有大规模 SFT 数据的原因**。8 条数据下 GRPO 难提升准确率是**数据量本质限制**，不是代码错。

## Q6: 为什么用 `0/1 严格奖励` 不用 partial credit？

**当前奖励**：
```python
rewards.append(1.0 if pred == truth else 0.0)  # 命中 1.0, 不命中 0.0
```

**备选**：
```python
rewards.append(0.5 if "正面" in text else 0.0)  # 格式对但分类错 = 0.5
```

**选 0/1 严格的理由**：
- 教学最直观（"对 vs 错"）
- partial credit 难设计（"差多少算 0.5？"）
- 我们的 system prompt 已经约束"必须三选一"，模型不答三选一就是 prompt-following 失败，应该重罚（0.0）

工业界有更复杂的奖励（format reward + accuracy reward 加权），但**教学最小示例从最简单开始**。

---

## 总结：3 个原则

1. **够用就好** —— 8 条数据、20 step、66.7% 准确率都够"打通链路"的目标
2. **最小可工作** —— 优先选最简单可行的方案（FP32 > BF16；TRL > verl；messages > Alpaca）
3. **理由可解释** —— 每个决策都有"为什么"，不为了酷炫而选复杂方案
