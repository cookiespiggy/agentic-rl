# 04 - 多步任务改造方案

> **本文档目的**：说明如何把 minimal-verl 从"判别任务示例"改造为"策略任务示例"，让示例本身就能证明 Agentic RL 的不可替代性。
>
> **状态**：设计方案 + 可运行代码骨架。环境与奖励部分已通过单元测试；训练脚本需在本地 macOS 环境验证后提交。

---

## 4.1 为什么需要改造

当前示例的任务是**中文情感三分类**。按 [25 章](../../25-判别能力外置-什么时候不该用RL.md) 的判据：

| 判据 | 情感分类 | 结论 |
|------|---------|------|
| 单步还是多步？ | 单步 | 判别类 |
| 输出是闭集吗？ | 是（3 类） | 判别类 |
| 有信用分配吗？ | 无 | 判别类 |

**三项全部命中判别类特征。** 这意味着它可以用一个 Schema 直接解决，不需要训练。

这带来一个尴尬：**一个 Agentic RL 教程的示例任务，本身不需要 Agentic RL。**

不过这个示例的价值是真实的——它验证了工具链（TRL 能否在本机跑通 SFT → GRPO）。本文档不替换它，而是**新增一个策略任务示例**。

---

## 4.2 判据回顾：什么样的任务"必须"用 RL

一个任务要真正体现 RL 的价值，需要同时满足：

1. **多步轨迹**：决策不是一次性的，后续步骤依赖前面步骤的结果
2. **延迟或稀疏奖励**：最终结果的好坏，不能由单步判断得出
3. **存在探索空间**：同一个目标有多条路径，需要"发现"更好的那条

**三者缺一，就不必用 RL。**

---

## 4.3 三个候选任务

| 任务 | 轨迹长度 | 信用分配 | 实现复杂度 | 推荐度 |
|------|---------|---------|-----------|--------|
| **多轮信息收集** | 2–5 轮 | 强 | 中 | ★★★ |
| 猜数字（二分搜索） | 3–7 步 | 强 | 低 | ★★★ |
| 工具调用 + 重试 | 2–5 步 | 中 | 中高 | ★★ |

**推荐「多轮信息收集」**，理由：

- 最贴近真实 Agent 场景（客服、助手、订票）
- 可复用现有的 ChatML 数据格式
- 策略空间清晰（"该问什么、问几次"），便于观察 RL 效果
- 环境是纯 Python，无外部依赖

## 4.4 推荐方案：多轮信息收集

### 4.4.1 任务定义

**场景**：用户给出不完整请求，Agent 需通过追问集齐必要信息后才能给出方案。

```text
用户：帮我订个餐厅
Agent：请问在哪个城市？
用户：上海
Agent：几位用餐？
用户：4 位
Agent：什么时间？
用户：今晚 7 点
Agent：好的，为您预订上海今晚 7 点、4 人的餐厅。   ← 完成
```

**必要槽位**（必须集齐 3 个）：`city` / `people` / `time`

**动作空间**（2 种）：

| 动作 | 语义 |
|------|------|
| `ask(slot)` | 追问某个槽位 |
| `answer(content)` | 给出最终方案 |

**为什么这需要 RL 而不是 Schema**：

- "问什么、按什么顺序问、什么时候该停"是一个**策略**问题，不是判断问题
- 同一个目标有多条路径（先问城市还是先问人数），存在探索空间
- 最终能否成功，取决于**整条轨迹**，不取决于任何单步判断

### 4.4.2 环境实现

> 完整实现见 [`rl/env.py`](../rl/env.py)，单元测试见 [`tests/test_env.py`](../tests/test_env.py)。

```python
# env.py
REQUIRED_SLOTS = ("city", "people", "time")


class InfoCollectionEnv:
    """多轮信息收集环境：Agent 需通过追问集齐必要槽位。"""

    def __init__(self, case, max_turns=5):
        self.case = case                    # {"request": "...", "slots": {...}}
        self.max_turns = max_turns
        self.collected = {}                 # 已集齐的槽位
        self.turns = 0

    def step(self, action):
        """返回 (observation, reward, done)。"""
        self.turns += 1
        kind = action.get("type")

        if kind == "ask":
            slot = action.get("slot")
            if slot in REQUIRED_SLOTS and slot not in self.collected:
                self.collected[slot] = self.case["slots"][slot]
                return self._obs(), 0.2, False       # 问对了
            return self._obs(), -0.2, False          # 重复或无关

        if kind == "answer":
            complete = len(self.collected) == len(REQUIRED_SLOTS)
            return self._obs(), (0.4 if complete else -0.5), True

        return self._obs(), -0.3, False              # 非法动作

    def succeeded(self):
        return len(self.collected) == len(REQUIRED_SLOTS)

    def _obs(self):
        return {
            "turns": self.turns,
            "collected": dict(self.collected),
            "remaining": [s for s in REQUIRED_SLOTS if s not in self.collected],
        }
```

### 4.4.3 两种奖励模式

**模式 A · 密集奖励**（每步即时反馈）

直接使用 `step()` 返回的 reward，累加为轨迹回报。

- 优点：信号密集，训练稳定，容易看到 reward 上升
- 缺点：**信用分配被削弱**——模型可能学会"多问几次拿小奖励"而不是"尽快完成任务"

**模式 B · 稀疏奖励**（只在结束时给）

```python
def episode_return(actions, case):
    """整条轨迹只在最后给一次奖励。"""
    env = InfoCollectionEnv(case)
    for a in actions:
        _, _, done = env.step(a)
        if done:
            break
    return 1.0 if env.succeeded() else 0.0
```

- 优点：**信用分配问题被完整暴露**，最接近真实的 RLVR 场景
- 缺点：信号稀疏，需要靠 GRPO 的组内比较来区分轨迹优劣

**建议：两种都实现，先跑模式 A 确认链路，再切模式 B 观察差异。** 这个对比本身就是极好的教学素材。

### 4.4.4 数据格式

沿用现有的 ChatML 结构，只需扩展字段：

```jsonl
{"messages": [{"role": "user", "content": "帮我订个餐厅"}],
 "case": {"request": "帮我订个餐厅", "slots": {"city": "上海", "people": "4", "time": "今晚7点"}}}
```

## 4.5 技术约束：TRL 是单轮生成器

**这是改造中最需要注意的一点。**

`GRPOTrainer` 的 `reward_funcs` 接收的是**模型生成的一个 completion**，而不是一条多轮轨迹。而多轮任务需要"生成 → 执行 → 再生成"的循环。

### 路径 A · 单轮生成完整计划（推荐先做）

让模型**一次性生成完整行动计划**，reward 在环境里执行整条计划：

```python
import json

def reward_fn(completions, case, **kwargs):
    rewards = []
    for comp, c in zip(completions, case):
        try:
            actions = json.loads(comp)      # 期望模型输出 JSON 数组
        except json.JSONDecodeError:
            rewards.append(-1.0)            # 格式错误直接罚
            continue
        rewards.append(episode_return(actions, c))
    return rewards
```

期望的模型输出：

```json
[{"type": "ask", "slot": "city"},
 {"type": "ask", "slot": "people"},
 {"type": "ask", "slot": "time"},
 {"type": "answer", "content": "上海今晚7点4人"}]
```

**权衡**：
- ✅ 兼容所有 TRL 版本，实现简单，几小时可跑通
- ✅ 奖励仍基于**轨迹执行结果**，能验证"轨迹质量 → 回报"的映射
- ❌ 不是真正的环境交互，credit assignment 较弱（一次生成）

### 路径 B · 真正的多轮交互

使用 TRL 的多轮支持（`environment_factory` / `rollout_func`，注意对版本有要求）。

**权衡**：
- ✅ 真多轮、真信用分配，是完整的 Agentic RL
- ❌ 需要较新的 TRL 版本，调试复杂度显著上升
- ❌ 训练时间成倍增加（每轮都要前向）

**建议：先 A 后 B。** 路径 A 足以验证"策略任务需要 RL"这个命题。

## 4.6 关键验证点：GRPO 应该显著优于 SFT

这是本次改造**最有价值的设计**。

对比当前示例的结果：

| 任务类型 | SFT 表现 | GRPO 相对 SFT |
|---------|---------|--------------|
| 情感分类（判别类） | 66.7% | **持平**（8 条数据下提升空间有限） |
| 多轮信息收集（策略类） | 待测 | **应显著提升** |

**为什么会有这个差异？**

- 情感分类是**知识问题**：模型知道"这句子是好评"就够了，SFT 已经把知识教进去了，RL 无事可做
- 多轮信息收集是**策略问题**：模型知道"要问城市"，但**不知道"什么时候该停止追问"**——这个需要试错才能学会

**所以：**

> **GRPO 能否超过 SFT，正是判别任务与策略任务的分水岭。**

如果改造后的示例里 GRPO 明显超过 SFT，那这个示例就**自证了 Agentic RL 的必要性**——这比任何文字论证都有力。
